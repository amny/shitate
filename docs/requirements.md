# TipTapリッチテキストエディター 要件定義書

Sep 30, 2026 · @天野　陽介

## 1. 概要・目的

AIで作成したシステム開発ドキュメント（要件定義書・仕様書など）を、TipTapベースのリッチテキストエディターで編集し、顧客に納品できる単体HTMLとして出力する。

- 納品後の指摘修正を、HTMLを直接触らずにリッチテキストで行えるようにする
- 納品したHTMLファイル自体を編集元とし、再読込して編集を再開できるようにする
- 見出し採番・目次・図表番号・相互参照など、仕様書に必要な体裁を自動で整える
- 必要に応じてページ番号付きのPDFを出力できるようにする

## 2. 利用者と利用シーン

主な利用者は自分自身で、有用であれば社内メンバーにも展開する。

**基本フロー**

1. AIに文書をMarkdown・HTML・TipTap JSONのいずれかで出力させる
2. エディターに手動で読み込み、体裁を整える
3. テーマを選び、単体HTMLとしてエクスポートして納品する
4. 顧客から指摘が入ったら、納品したHTMLをエディターに読み込み直して修正する
5. 改訂履歴を追記し、再度エクスポートして納品する

納品物はブラウザで閲覧される。紙への印刷はしないが、PDF化が必要になる場合がある。

## 3. スコープ

| 区分 | 項目 |
| --- | --- |
| 対象 | Markdown / HTML / TipTap JSONの読込 |
| 対象 | リッチテキスト編集（表のセル結合、セル内の箇条書き・画像を含む） |
| 対象 | 仕様書向け機能（見出し採番、目次、図表番号、相互参照、表紙、改訂履歴） |
| 対象 | 単体HTMLのエクスポートと再読込 |
| 対象 | ページ番号付きPDFの出力 |
| 対象 | テーマの選択・編集・追加 |
| 対象 | ブラウザへの自動一時保存 |
| 対象外 | AIとの連携機能（エディター内でのAI呼び出しなど） |
| 対象外 | サーバーでの永続保存、複数人での同時編集 |
| 対象外 | 紙への印刷を前提とした体裁調整 |

## 4. 機能要件

### 4.1 入力

- Markdown、HTML、TipTap JSONのファイルを読み込める
- GFMの表ではセル結合やセル内の箇条書き・画像を表現できないため、複雑な表を含む文書はHTMLかJSONで出力させる運用とする
- 本エディターがエクスポートしたHTMLを読み込んだ場合は、埋め込まれた編集用データから完全に復元する（4.6参照）

### 4.2 基本編集

- 見出し（H1〜H6）、段落、太字・斜体・下線・取り消し線、箇条書き・番号付きリスト、引用、コードブロック、リンク、画像、水平線
- 元に戻す・やり直し
- ショートカットはTipTapの `Mod-` 表記で定義し、WindowsのCtrlとMacの⌘の違いを吸収する

### 4.3 表

- 行・列の追加と削除、列幅の変更
- セルの結合（colspan / rowspan）と分割
- セル内に箇条書き・番号付きリスト・画像を配置できる
- 表の入れ子を許可するかは未決（9章の要検証事項）

### 4.4 仕様書向け機能

| 機能 | 要件 | 実現方針 |
| --- | --- | --- |
| 見出し採番 | H1〜H5を「1.2.3.4.5」形式で自動採番し、H6は採番しない | 採番はJSで計算し、エディターではデコレーションで表示、エクスポート時にHTMLへ書き込む |
| 目次 | 見出しから自動生成し、リンク付きで出力する。目次に載せる深さは採番の深さとは別に設定でき、初期値は3階層 | 目次ノードを1つ置き、採番と同じ計算結果を使う |
| 図表番号・キャプション | 図と表に「図1」「表1」の番号とキャプションを付ける | キャプション付きのカスタムノード（figure / table + caption）で包む |
| 相互参照 | 「2.1節参照」「表3参照」などの参照を置け、番号が変わると自動で追従する | 参照先IDを持つインラインノード。見出し・図・表に安定IDを振り、コピペ時の重複IDは振り直す。参照先が削除されたら「参照先なし」と警告表示する |
| 表紙 | タイトル、案件名、版数、日付、会社名などを入力して表紙を生成する | 本文とは別の文書メタデータとしてフォームで入力し、テーマ側のテンプレートで描画する |
| 改訂履歴 | 版・日付・内容・担当の一覧を管理し、表として出力する | 構造化データとして持ち、自由編集の表にはしない |

### 4.5 テーマ

- ビルトインテーマを複数用意し、選択できる
- テーマは1本のCSSテキストとし、文書部分をルートクラス（例：`.doc`）の中にスコープする
- エディター画面とエクスポートで同じテーマCSSを使い、見た目を一致させる
- エディターのUI部分（選択枠、列幅変更ハンドルなど）はテーマとは別のCSSにする
- ビルトインテーマを編集すると、元を残してコピーをユーザーテーマとして保存する。いつでも初期状態に戻せる
- ユーザーテーマの追加・複製・削除と、テーマ単体のインポート・エクスポートができる

**ヘッダー・フッター（会社ロゴ、Copyright）**

位置と見た目はテーマCSSで決め、中身は設定値として分けて持つ。年の変更や別会社のロゴ表示のたびにテーマを複製しなくて済むようにするため。

| 持つ場所 | 内容 |
| --- | --- |
| テーマCSS | ヘッダー・フッターの位置、サイズ、フォント、区切り線 |
| テーマ設定値（テーマごとの既定値） | ロゴ画像、Copyright文言 |
| 文書メタデータ（文書ごとに上書き可） | 顧客名など、案件ごとに変わる値 |

- エクスポート時に、設定値をCSS変数（例：`--header-logo`、`--copyright`）として `<style>` に注入する。テーマCSSは変数を参照するだけにする
- ロゴ画像はData URI（Base64）で持ち、単体ファイル完結の方針を守る
- ブラウザ表示では、エクスポート時に `<header>` / `<footer>` 要素として文書の先頭と末尾に1回だけ出力する（擬似要素だと選択・コピーできないため使わない）

### 4.6 エクスポートと再読込

- CSSと画像（Base64）を埋め込んだ、1ファイルで完結するHTMLとして出力する
- 出力順は、表紙 → 改訂履歴 → 目次 → 本文（採番済み）とする
- 編集用データ（TipTap JSON、表紙情報、改訂履歴、テーマID）を `<script type="application/json">` で埋め込む。ブラウザ表示では見えないこと
- 読込時は埋め込みデータを優先して復元する
- ブラウザで閲覧するときは、ページ分割しない通常表示とする

### 4.7 PDF出力

- アプリ内に「PDFプレビュー」モードを設け、組版ライブラリでページ分割してからブラウザの印刷機能でPDFに保存する
- ページ番号を入れる。目次にもページ番号を表示する
- 表紙・改訂履歴・目次の後で改ページし、表や図の途中では改ページしない
- PDF化のときだけ日本語フォントを統一する（Webフォントを指定）
- エディター表示とPDFの差異は、改行位置のずれなど誤差レベルであれば許容する

**ページのヘッダー・フッター**

- `@page` の余白ボックス（`@top-left`、`@bottom-center` など）に、ロゴ、Copyright、ページ番号を配置する
- ヘッダーに現在の章タイトル（柱）を表示する（`string-set` を使用）
- 表紙ページにはヘッダー・フッターを表示しない（`@page :first`）

```css
@page {
  @top-left     { content: var(--header-logo); }
  @top-right    { content: string(chapter); }
  @bottom-left  { content: var(--copyright); }
  @bottom-right { content: counter(page) " / " counter(pages); }
}
@page :first { @top-left { content: none; } }
h1 { string-set: chapter content(); }
```

**ページ設定**

紙への印刷は前提としないため、A4に固定しない。画面で読むPDFでは、1ページの情報量は用紙サイズよりも「ページ幅に対する文字サイズ」と余白で決まるので、それらを設定として持つ。

| 設定 | 選択肢 | 持つ場所 |
| --- | --- | --- |
| ページサイズ | A4 / A3 / B4、縦 / 横、カスタム（mm指定） | テーマ設定値（文書ごとに上書き可） |
| 余白 | 狭い / 標準 / 広い | テーマ設定値（文書ごとに上書き可） |
| 本文の基準文字サイズ | 9pt〜12pt | テーマ設定値（文書ごとに上書き可） |
| 横向きページ | 幅の広い表だけを横向きのページに配置する | 表ごとの属性 |

- 既定値はA4縦・標準余白・10.5pt
- 用紙サイズはA判・B判のプリセットを基本とし、顧客側で印刷されてもそのまま使えるようにする
- `@page` の `size` はCSS変数での指定が不安定なため、設定値からエクスポート時に `@page` ルールを生成する
- カスタムサイズと名前付きページ（横向きページ）の対応状況は、PDF組版ライブラリのスパイクで検証する

### 4.8 一時保存

- 編集中の内容をIndexedDBへ自動保存し、ブラウザを閉じても消失しないようにする
- 画像をBase64で持つとlocalStorageの容量を超えるため、localStorageは使わない
- 永続保存は行わない。保存の正本はエクスポートしたHTMLとする

## 5. 非機能要件

| 項目 | 要件 |
| --- | --- |
| 対応OS | Windows、Mac |
| 動作保証ブラウザ | Chrome、Edge（Safariは動作保証外） |
| 提供形態 | 当面はローカルサーバーを起動してブラウザでアクセスする。将来Electronでデスクトップアプリ化する |
| フォント | エディター表示はOS標準フォントでよい。PDF化のときだけWebフォントで統一する |
| 日本語入力（IME） | 独自のキー処理を書くときは `isComposing` で変換中かを必ず判定し、変換確定のEnterを誤処理しない |
| 貼り付け | Excel・Wordからの表の貼り付けに対応するかは未決（9章） |
| データ消失防止 | 編集内容を自動保存し、ブラウザを閉じたり再読込したりしても復元できる |

## 6. データ設計

エクスポートHTMLは「表示用の本文」と「復元用の編集データ」を1ファイルに同居させる。表示部分は採番済みの静的HTML、復元は埋め込みJSONから行う。

```html
<html>
  <head>
    <style>テーマCSS（画面用 + 印刷用）</style>
  </head>
  <body>
    <div class="doc">
      表紙 → 改訂履歴 → 目次 → 本文（採番済み）
    </div>
    <script type="application/json" id="doc-data">
      { "version": 1, "doc": {TipTap JSON}, "meta": {表紙情報},
        "revisions": [改訂履歴], "theme": {"id": "..."} }
    </script>
  </body>
</html>
```

| データ | 内容 | 保存先 |
| --- | --- | --- |
| doc | 本文のTipTap JSON。見出し・図・表は安定IDを持つ | 埋め込みJSON、IndexedDB |
| meta | 表紙の項目（タイトル、案件名、版数、日付、会社名など） | 埋め込みJSON、IndexedDB |
| revisions | 改訂履歴（版・日付・内容・担当） | 埋め込みJSON、IndexedDB |
| theme | 使用テーマのID。テーマCSS本体は `<style>` に埋め込む | 埋め込みJSON、IndexedDB |
| themes | ユーザーテーマの一覧（CSSテキスト） | IndexedDB、テーマ単体ファイル |

- 埋め込みJSONには形式のバージョン番号を持たせ、将来の形式変更に備える
- 読み込んだHTMLのテーマIDが手元にない場合は、`<style>` のCSSからテーマを復元する

## 7. 技術スタックとアーキテクチャ方針

React + Vite + TipTapで作り、ファイル入出力と保存をアダプター層に閉じ込めて、Electron化のときに差し替えられるようにする。

デスクトップ化で差し替えるのは最下段の実装だけで、UI・エディター・変換処理はWeb版と共通のまま使う。

| 領域 | 採用技術 | 備考 |
| --- | --- | --- |
| フロントエンド | React、Vite、TypeScript |  |
| エディター | TipTap（Table拡張など）＋カスタム拡張 | 表機能の内部はprosemirror-tables |
| Markdown読込 | TipTapのMarkdown対応（公式またはコミュニティ拡張） | 実装時に最新状況を確認する |
| 一時保存 | IndexedDB |  |
| PDF組版 | Vivliostyle または Paged.js | 9章でスパイク検証して選定する |
| デスクトップ化 | Electron | Chromiumを同梱し、WindowsとMacで描画・組版の挙動を揃える |

**Electronを選ぶ理由**：TauriはOS標準のWebViewを使うため、Windows（WebView2）とMac（WKWebView）で描画・組版の挙動が変わる。過去にTauri + Paged.jsでのPDF化がこの差異で行き詰まった経緯があり、PDF出力を要件に含む本ツールではElectronを採用する。

**カスタム拡張の一覧**

- 見出し採番プラグイン（デコレーション）
- 目次ノード
- 図ノード（画像 + キャプション）、表ラッパーノード（表 + キャプション）
- 相互参照ノード
- 安定ID付与プラグイン（重複時に振り直し）

**アダプター層**：「ファイルを開く」「ダウンロード・保存」「一時保存」をインターフェースとして定義し、Web版はブラウザAPI、Electron版はNode.jsのファイルAPIで実装する。

## 8. フェーズ計画

リスクが高い「表の編集」と「エクスポートと再読込の往復」を最初に検証し、仕様書化・テーマ管理・デスクトップ化の順に積み上げる。

| フェーズ | 内容 | 完了の目安 |
| --- | --- | --- |
| Phase 1：編集と出力の核 | 3形式の読込、基本編集、表（セル結合、セル内の箇条書き・画像）、埋め込みデータ付きHTMLのエクスポートと再読込、IndexedDBへの自動保存、ビルトインテーマ1〜2種 | 納品HTMLを読み込み直して、欠落なく編集を再開できる |
| Phase 2：仕様書化 | 見出し採番、目次、図表番号・キャプション、相互参照、表紙、改訂履歴、PDFプレビューとPDF出力 | ページ番号付きの目次を持つPDFを出力できる |
| Phase 3：テーマ管理 | テーマ編集画面、テーマの追加・複製・削除、テーマのインポート・エクスポート | ビルトインを編集しても初期状態に戻せる |
| Phase 4：デスクトップ化 | Electron化、アダプター層の差し替え | WindowsとMacで同じPDFが出力できる |

Phase 2の着手前に、PDF組版ライブラリのスパイク検証（9章）を行う。

## 9. 技術リスクと要検証事項

最大のリスクは、ページ番号付き目次を含むPDF組版であり、Phase 2の前にスパイクで検証する。

| 項目 | 内容 | 対応 |
| --- | --- | --- |
| PDF組版ライブラリ | 目次へのページ番号表示はChrome標準では難しく、組版ライブラリが必要。Paged.jsは更新頻度に注意、Vivliostyleは日本語組版に強い | 両方でスパイクし、採番・相互参照・結合セルの表を含むサンプル文書で比較して選定する |
| 表の編集操作 | 結合セルを含む範囲のコピペや、列幅変更との組み合わせで挙動が崩れる可能性がある | Phase 1で重点的にテストする |
| 画像の配置方式 | 画像をinlineとblockのどちらで扱うかで、表内での挙動が変わる | Phase 1の設計時に決める |
| 表の入れ子 | 表の中に表を許可するか | 許可する |
| 表内画像のキャプション | 表内に置いた画像を図番号の対象にするか | 対象にしない |
| Markdown読込 | TipTapのMarkdown対応の現状（公式かコミュニティ拡張か） | 実装時に確認する |
| Excel・Wordからの貼り付け | クリップボードのHTMLはOSやOfficeのバージョンで差がある | 対応範囲を決める（未決） |
| 埋め込みフォントのサイズ | 日本語Webフォントは容量が大きい | PDF化のときだけ読み込む。サブセット化も検討する |
